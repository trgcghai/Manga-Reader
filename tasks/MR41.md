# MR41: Global API Response Envelope

## Title
Standardize all API responses with a consistent success/error envelope.

## Description
Currently, the backend returns raw entities/DTOs directly. Errors use NestJS's default HTTP exception shape. The frontend has no unified way to handle errors. This task adds a global response wrapper:

- **Backend**: A `ResponseInterceptor` wraps all successful responses into `{ success, data, meta?, timestamp }`; an `ExceptionFilter` catches all exceptions and formats them as `{ success, error, timestamp }`
- **Frontend**: An Axios response interceptor validates the envelope and unwraps `data` for success, rejects with the structured error shape on failure

## Proposed Envelope Shape

### Success Response
```json
{
  "success": true,
  "data": <existing payload>,
  "meta": { "total": 100, "page": 1, "limit": 20, "totalPages": 5 },
  "message": "optional success message",
  "timestamp": "2026-06-14T12:00:00.000Z"
}
```

### Error Response
```json
{
  "success": false,
  "data": null,
  "error": {
    "code": 404,
    "message": "Not Found",
    "details": ["Manga with ID 999 not found"]
  },
  "timestamp": "2026-06-14T12:00:00.000Z"
}
```

The `data` field inside success is the **exact same payload** returned today (raw entity, pagination object, import result, blob, etc.). The envelope wraps around it without changing response content.

## Requirements

### Backend: ResponseInterceptor
- Implements `NestInterceptor` — wraps `200`/`201` responses in `{ success: true, data, meta?, message?, timestamp }`
- Extracts `meta` from a `@SetMetadata('responseMeta', ...)` decorator for paginated endpoints
- Extracts `message` from a `@SetMetadata('responseMessage', ...)` decorator
- Skips wrapping for `StreamableFile` (file downloads — keep raw binary)
- Preserves `@HttpCode()` and `@Res()` decorator behavior

### Backend: ExceptionFilter
- Implements `ExceptionFilter<HttpException>` — catches all `HttpException` instances
- Catches unhandled errors too (catch-all for non-HTTP exceptions, returns 500)
- Formats as `{ success: false, data: null, error: { code, message, details }, timestamp }`
- For `BadRequestException` with validation errors, `details` should be the validation error array from NestJS

### Backend: Registration
- Register both interceptor and filter globally in `app.module.ts` using `APP_INTERCEPTOR` and `APP_FILTER` providers
- Order matters: filter must be registered before interceptor so errors never reach the interceptor

### Frontend: Axios Response Interceptor
- Add an interceptor in `frontend/src/services/api/api.ts`
- On success (`response.data.success === true`): return `response.data.data` as the resolved value, so `.then(data => ...)` receives the payload directly
- On application-level error (`response.data.success === false`): reject with `{ code, message, details }`
- On HTTP/network error (no response): reject with a generic error shape `{ code: 0, message: 'Network error', details: [] }`
- **Blob pass-through**: Skip unwrapping for requests with `responseType: 'blob'` (the download template endpoint)
- Define shared TypeScript interfaces for the envelope (`ApiSuccessResponse<T>`, `ApiErrorResponse`, `ApiError`)

### Frontend: Update API Functions
- All API functions (`mangaApi.ts`, `authorApi.ts`, `genreApi.ts`, `translatorApi.ts`, `languageApi.ts`) currently do `const { data } = await axiosInstance.get<T>(url); return data`
- With the interceptor unwrapping, change to `return await axiosInstance.get<T>(url)` — the promise resolves to `T` directly
- For `deleteManga` (returns `void` currently, status 204 with no body): the interceptor should pass through 204 responses without trying to unwrap

### Frontend: Hook-level Error Handling (optional but recommended)
- Create a reusable `useApiMutation` or extend existing hooks to extract `{ code, message, details }` from rejected errors and surface them in a consistent toast/notification
- Create an `ApiErrorDisplay` component that renders the structured error in the UI (used in data-fetching routes)

## Implementation Order

2. **Backend**: Add `@SetMetadata('responseMeta', ...)` to paginated controllers (manga, author, genre, translator list endpoints)
3. **Backend**: Verify all tests pass with new envelope
4. **Backend**: Remove old `ScanImagesResult` types from chapter constants (dead code — `chapter.constant.ts` already kept)
5. **Frontend**: Add Axios interceptor + envelope types to `api.ts`
6. **Frontend**: Update all API functions (remove `const { data } =` destructure, return `axiosInstance.get<T>` directly)
7. **Frontend**: Verify all frontend tests pass

## Testing Notes

- Existing backend unit tests will need their expectations updated — if a test expects raw `{ data: [...], total }`, it now needs to expect `{ success: true, data: { data: [...], total }, timestamp }` instead
- Consider skipping the timestamp field in test assertions (use `expect.objectContaining({ success: true, data: ... })`)
- Interceptor/filter unit tests should cover: success wrapping, pagination meta, validation error details, 404 error, 500 unhandled error, StreamableFile passthrough
- Frontend API functions don't need test changes if the interceptor correctly unwraps — the returned type is the same as before

## Notes
- The `meta` field is only present when explicitly set via `@SetMetadata`. For single-entity responses, `meta` is omitted from the envelope.
- The `message` field is optional and only set via `@SetMetadata('responseMessage', ...)`.
- `DELETE /mangas/:id` returns 204 with no body — the interceptor should skip wrapping for 204/no-content responses.
- File download (`GET /mangas/import-template`) must not be wrapped since it returns a binary stream.
