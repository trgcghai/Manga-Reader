# Repository Guidelines

## Project Structure

- `backend/` contains the NestJS + TypeScript API. Application code and Jest specs live under `backend/src/`; specs use `*.spec.ts`.
- `frontend/` contains the TanStack Start + Vite + React app. Routes, components, hooks, stores, utilities, and Vitest specs live under `frontend/src/`.
- `frontend/src/routeTree.gen.ts` is generated by `npm run generate-routes`; do not edit it by hand.
- `docker-compose.yml` runs the development stack. `docker-compose.production.yml` and `.env.production.example` are production deployment configuration.
- Keep manga libraries outside the repository. `overview.md` describes the product scope.

## Build, Test, and Development

- Full stack: `docker compose up --build` builds and starts the development services. Source is copied into images, so rebuild after source changes.
- Backend, from `backend/`: `npm ci`, `npm run start:dev`, `npm run build`, `npm test -- --runInBand`, and `npm run test:e2e`.
- Frontend, from `frontend/`: `npm ci`, `npm run dev`, `npm run generate-routes`, `npm run build`, and `npm test`.
- Run focused tests by naming the spec, for example `npm test -- file.service.spec.ts`.

## Style and Naming

Use TypeScript, two-space indentation, and the existing Prettier/ESLint configuration. Keep Nest modules grouped by feature; use descriptive names such as `manga.service.ts` and `manga.service.spec.ts`. Use clear component names and keep route files aligned with their URL paths. Run the package's formatter or linter before submitting related changes.

## Tests

Backend tests use Jest; frontend tests use Vitest and React Testing Library. Add or update nearby `*.spec.ts` / `*.spec.tsx` files for behavior changes. Prefer small fixtures for file discovery, archive metadata, language selection, and reading progress. Run the relevant focused suite, then the build when practical.

## Commits and Pull Requests

Recent commits use short, lowercase prefixes such as `feat:`, `fix:`, `refactor:`, and `docs:`. Keep each commit focused. A pull request should explain the change and its user impact, list verification commands and results, link a related issue when available, and include screenshots for visible UI changes.
Do not commit until be asked for.

## Configuration and Scope

Never commit `.env` files, credentials, or user manga data. Update `.env.example` files when configuration changes. Keep the app local-first and offline-capable; do not add telemetry, cloud sync, or internet-backed services without an explicit product-scope change.
